今日の重要トピックKey topics today

  1. WebXR Input Profiles Registry は profile id、fallbackProfileIds、handedness layout、components、selectComponentId、gamepad button / axes mapping を定義し、User Agent とアプリの入力解釈をそろえる基準になります。 The WebXR Input Profiles Registry defines profile ids, fallbackProfileIds, handedness layouts, components, selectComponentId, and gamepad button/axes mappings, aligning input interpretation between user agents and applications.
  2. motion-controllers package の `fetchProfile()` は `profilesList.json` を起点に `XRInputSource.profiles` の先頭から一致 profile を探すため、network / CDN / local bundle の失敗時 fallback 設計が必要です。 The motion-controllers package `fetchProfile()` starts from `profilesList.json` and scans `XRInputSource.profiles` from the front, so network, CDN, and local-bundle failure routes need to be designed explicitly.
  3. MDN の `XRInputSource.profiles` は、profile 配列が具体度順であることと、inline mode では常に空配列になることを明記しており、inline と immersive の route を分ける根拠になります。 MDN's `XRInputSource.profiles` notes that the array is ordered by specificity and is always empty in inline mode, which justifies separating inline and immersive routing.
  4. WebXR Device API の inline session は通常ページ内表示と入力検証に使える一方、XR controller の Registry 解決までは期待しすぎないほうが安定します。 The WebXR Device API inline session is useful for page-embedded display and input checks, but it should not be expected to resolve XR controller Registry data.
  5. Immersive Web Samples の Controller State は gamepad attribute の可視化例として有用ですが、今日の公開カードは外部デモではなく、ワークスペース内の Registry fetch probe と inline event logger を中心にしました。 Immersive Web's Controller State sample is useful as a gamepad-attribute visualization reference, while today's public cards remain centered on the original Registry fetch probe and inline event logger in this workspace.

注目事例と何が面白いかNotable example and why it matters

今日の注目は、Immersive Web の WebXR Input Profiles Registry と motion-controllers package です。Registry は profile 名の一覧ではなく、handedness ごとの layout、component、selectComponentId、gamepad mapping を持つため、controller を device 固有分岐ではなく semantic action に変換する土台になります。面白い点は、実 profile fetch が失敗しても、reported profiles の順序、generic fallback、inline mode の空 profiles を分ければ、ユーザー操作の route を説明可能な状態で縮退できることです。

Today's notable references are Immersive Web's WebXR Input Profiles Registry and motion-controllers package. The Registry is more than a list of profile names: it carries handedness-specific layouts, components, selectComponentId, and gamepad mappings, making it a foundation for converting controllers into semantic actions without device-specific branching. The interesting part is that even when real profile fetching fails, the app can degrade explainably by separating reported-profile order, generic fallback, and empty profiles in inline mode.

制作に使えそうな技術メモProduction note

`XRInputSource.profiles` は具体度順の候補列として扱い、アプリ側は先頭から対応 profile を探します。`profilesList.json` が取れない場合に備え、よく使う generic profile だけはローカル seed として持つと入力が完全停止しません。inline mode では profiles が空になるため、Registry route ではなく DOM pointer / screen select の route を明示します。実装時は remote fetch、local bundle、inline fallback、unknown profile fallback を別 metric にして、どこで縮退したのかをログ化すると検証しやすくなります。

Treat `XRInputSource.profiles` as an ordered candidate list and search from the front. Keeping a small local seed of common generic profiles prevents input from fully stopping when `profilesList.json` cannot be fetched. Because profiles are empty in inline mode, route to DOM pointer or screen select rather than the Registry route. In production, track remote fetch, local bundle, inline fallback, and unknown-profile fallback as separate metrics so the degradation point is visible in logs.
