今日の重要トピックKey topics today

  1. WebXR の入力は、デバイス形状より先に `targetRayMode` の `screen` / `gaze` / `tracked-pointer` で整理すると、表示すべき hint を決めやすい。 WebXR input becomes easier to route by considering `targetRayMode` values such as `screen`, `gaze`, and `tracked-pointer` before device shape.
  2. `XRSession.inputSources` はアクティブな `XRInputSource` の一覧で、追加・削除時には `inputsourceschange` を見てキャッシュを更新する必要がある。 `XRSession.inputSources` lists active `XRInputSource` objects, and applications should refresh cached input state on `inputsourceschange`.
  3. `selectstart` / `select` / `selectend` と `squeezestart` / `squeeze` / `squeezeend` は primary action と secondary/grab action を分ける軸になる。 `selectstart` / `select` / `selectend` and `squeezestart` / `squeeze` / `squeezeend` separate primary action from secondary or grab-style action.
  4. WebXR Input Profiles registry は、ハードウェア固有 profile から generic fallback までの ordered list を持ち、モデル表示や gamepad mapping を安定させるための一次情報になる。 The WebXR Input Profiles registry provides ordered hardware-specific and generic fallback profiles that stabilize model rendering and gamepad mapping.
  5. 公式 samples の Input Tracking / Input Profiles は実装確認に有用だが、公開アーカイブでは外部デモを並べず、自作サンプルで fallback policy と見え方の差を可視化する。 Official Input Tracking / Input Profiles samples are useful references, but the public archive centers the local original sample that visualizes fallback policy and hint differences.

注目事例と何が面白いかNotable example and why it matters

今日の注目は WebXR Input Profiles です。これは派手な表示サンプルではなく、`XRInputSource.profiles`、`handedness`、`gamepad` mapping、fallback profile をそろえるための registry / assets / helper library の集合です。面白いのは、アプリが特定コントローラー名に賭けるのではなく、ordered profile list をたどって「正確なモデル」「generic controller」「抽象 silhouette」へ段階的に落とせる点です。今日の自作サンプルでは、この発想を入力ルーターとして可視化しました。

Today's notable reference is WebXR Input Profiles. It is not a flashy demo, but a registry/assets/helper-library set for aligning `XRInputSource.profiles`, `handedness`, `gamepad` mapping, and fallback profiles. The useful part is that an app can follow the ordered profile list and degrade from an exact model to a generic controller or abstract silhouette instead of betting on one controller name. Today's original sample turns that idea into an input router.

The sample switches between `screen`, `gaze`, `tracked-pointer`, and `hand`, then shows whether the virtual target should render a highlight, cursor, ray, or model. 制作に使えそうな技術メモProduction note

実装では `inputSources` を毎フレーム無条件に信じるより、`inputsourceschange` で preferred source を更新し、`targetRayMode` ごとに表示 hint を決める層を挟むと破綻しにくいです。`screen` は指で隠れるため highlight 中心、`gaze` は ray を出さず cursor / highlight、`tracked-pointer` は ray / cursor / model、hand は joint mesh や短い ray に寄せるとよいです。`XRFrame.getPose(inputSource.targetRaySpace, referenceSpace)` が `null` になる可能性と `XRPose.emulatedPosition` も、UI の信頼度表示に入れる価値があります。

In production, route input through an `inputsourceschange`-driven preferred-source layer and decide visual hints per `targetRayMode` rather than trusting all `inputSources` equally every frame. `screen` should lean on highlights because fingers obscure the view, `gaze` should avoid a ray and use cursor/highlight, `tracked-pointer` can use ray/cursor/model, and hand input can use joint meshes or shorter rays. Treat possible `null` poses from `XRFrame.getPose(inputSource.targetRaySpace, referenceSpace)` and `XRPose.emulatedPosition` as part of the UI confidence signal.

The selected prototype is `Input Profile Fallback Router`. It does not start a real XR session; instead it recreates `XRInputSource` concepts on a local canvas so the user can see hint and model fallback changes per input type. Next additions should include real fetching of Input Profiles JSON, a simulated gamepad button/axis binding table, arbitration between hand pinch and squeeze action, and duplicate-event suppression with DOM Overlay pointer events.
