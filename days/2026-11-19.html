今日の重要トピックKey topics today

  1. `supportedFrameRates` は更新要求に使える値の集合で、集合外の値は拒否される。 supportedFrameRates constrains valid update requests.
  2. `updateTargetFrameRate()` は希望値を伝える非同期操作で、実効 cadence を即時保証しない。 A target-frame-rate update is asynchronous rather than a guarantee of immediate cadence.
  3. trusted UI などでコンポジタが一時的に nominal frame rate を変えることがある。 The compositor may temporarily alter nominal rate.
  4. 一時的な低下を利用者の品質設定変更として保存せず、復帰時の遷移を設計する。 Temporary throttling must not become a persisted user preference.
  5. 品質予算は中心の操作対象、空間文脈、装飾の順に段階的に手放す。 Quality should hand off from flair to context while protecting the interaction core.

注目事例と何が面白いかNotable example and why it matters

2026年11月9日版 WebXR Device API は、session が対応する値を supportedFrameRates として公開し、集合外の updateTargetFrameRate() を TypeError で拒否します。また、コンポジタが visible-blurred のような理由で名目 frame rate を変えた後は、要因が解消すれば内部 target を使うことを求めます。本命はこの『希望』『実効』『一時的な割り込み』を同じ数字に畳まない自作実験です。

The main sample keeps supported intent, nominal cadence, and temporary compositor changes visibly distinct.

制作に使えそうな技術メモProduction note

実装では session.supportedFrameRates が存在するかを確認し、その要素だけを updateTargetFrameRate(rate) に渡します。promise が解決しても frame 間隔を決め打ちせず、XRFrame の到着と GPU 計測から実効予算を判断します。visibilitychange や device 状態で一時的に cadence が変わる場合、ユーザー設定・保存済み品質とは別の transient state として扱います。

Request only supported rates, observe real frame delivery, and keep transient throttling separate from persisted preference.

俯瞰メモBird's-eye memo

XR の frame rate は単純な速さの設定ではなく、ブラウザ・コンポジタ・コンテンツが共有する時間の境界です。希望した数値だけを UI に表示すると、trusted UI や熱・電力の都合で実効が変わったとき、アプリは誤った確信を持ちます。観測と表現の優先順位を分けると、性能低下を『壊れた体験』ではなく安全なモード遷移として扱えます。

Frame rate is a shared time boundary; separating intent and observation makes degradation a safe mode transition.
