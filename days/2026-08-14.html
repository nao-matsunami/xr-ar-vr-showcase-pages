今日の重要トピックKey topics today

  1. MDN の WebXR input guide は、XR input source が targeting と action を分け、追加の buttons / axes は `XRInputSource.gamepad` から読む前提を説明している。 MDN's WebXR input guide explains that XR input sources separate targeting from actions, while additional buttons and axes are read through `XRInputSource.gamepad`.
  2. W3C WebXR Gamepads Module Level 1 は XR controller 向けの `xr-standard` gamepad mapping を定義し、trigger、squeeze、thumbstick / touchpad を profile と結び付ける基礎になります。 The W3C WebXR Gamepads Module Level 1 defines the `xr-standard` gamepad mapping for XR controllers, forming the basis for linking trigger, squeeze, thumbstick / touchpad, and profiles.
  3. Gamepad API は button、axis、haptic actuator の一般モデルを定義しており、昨日の haptic mixer と今日の polling layer を同じ payload で接続しやすい。 The Gamepad API defines the general button, axis, and haptic actuator model, making yesterday's haptic mixer and today's polling layer easy to connect through one payload.
  4. Immersive Web の WebXR Samples には Controller State と Input Profiles の公式デモ入口があり、実機 controller の状態表示と profile 解決の挙動確認に使える。 Immersive Web's WebXR Samples include official Controller State and Input Profiles demo entry points for inspecting real controller state and profile resolution behavior.
  5. WebXR Input Profiles の motion-controllers package は、`inputsourceschange` で controller を作り、XR frame callback ごとに `updateFromGamepad()` する流れを示している。 The WebXR Input Profiles motion-controllers package shows a flow where controllers are created on `inputsourceschange` and `updateFromGamepad()` is called during each XR frame callback.

Today's notable references are the Immersive Web Controller State sample and the WebXR Input Profiles motion-controllers package. Select / squeeze events alone do not capture thumbstick, touchpad, trigger value, handedness, or profile-specific differences. Stable XR interaction needs a layer that reads `session.inputSources` in the XR frame loop, normalizes `inputSource.gamepad`, and routes the result into app actions, visual state, and haptic feedback.

表現・インタラクションのアイデアExpression and interaction idea

サンプルでは、左右 controller の重み、profile、trigger、squeeze、thumbstick x / y、deadzone、poll jitter を操作し、毎フレーム `hover`、`select`、`grab`、`idle` に落とします。canvas 上では dominant hand から照準線が伸び、正規化後の button / axis 値と haptic route が同じ payload から更新されます。実機がなくても、profile 変更による入力名の違いと action decision の境界を確認できます。

The sample lets you manipulate left/right controller weight, profile, trigger, squeeze, thumbstick x / y, deadzone, and poll jitter, then collapses each frame into `hover`, `select`, `grab`, or `idle`. On the canvas, an aim ray extends from the dominant hand, and normalized button / axis values plus haptic route update from the same payload. Without hardware, it still exposes profile naming differences and action decision thresholds.

制作に使えそうな技術メモProduction note

実装時は `inputsourceschange` で入力ソースの追加 / 削除を追跡し、XR frame callback で各 `inputSource.gamepad` を poll します。profile 解決は WebXR Input Profiles の registry / assets / motion-controllers を使うと、button index の直読みではなく conceptual component 単位に寄せられます。deadzone、value threshold、jitter 抑制、handedness、haptic support は input adapter で吸収し、アプリの placement / menu / warning ロジックには semantic action だけを渡すのが扱いやすいです。

In production, track input-source additions and removals with `inputsourceschange`, then poll each `inputSource.gamepad` inside the XR frame callback. WebXR Input Profiles registry / assets / motion-controllers help resolve profiles into conceptual components rather than raw button indices. Deadzones, value thresholds, jitter suppression, handedness, and haptic support should be absorbed by an input adapter, leaving placement / menu / warning logic to consume only semantic actions.
