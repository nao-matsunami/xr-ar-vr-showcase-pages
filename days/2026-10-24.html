今日の重要トピックKey topics today

  1. WebXR Device API は immersive session を transient activation 内で requestSession() する流れを示しています。 Immersive sessions are requested within transient user activation.
  2. XRSession.requestAnimationFrame() は tracking state と frame の主要な観測点で、window rAF と交換できません。 XRSession rAF, not window rAF, is the session frame observation.
  3. predictedDisplayTime は表示対象の予測時刻であり、アプリの render budget を直接示す値ではありません。 predictedDisplayTime is not a render-budget measurement.
  4. WebXR-WebGPU Binding の subimage は frame 内の render target なので、session frame の後に別 receipt として記録します。 WebGPU subimages belong to a subsequent frame-scoped receipt.

注目事例と何が面白いかNotable example and why it matters

W3C の基本 flow は、isSessionSupported() で表示可否を調べ、ユーザーの transient activation を待って requestSession() し、成功後に XRSession rAF を回します。ここで capability、開始意図、active session、frame 観測を同じ「XR が使える」という一語に畳まないことが、説明可能な fallback UI につながります。

The standard flow separates support, activation, session acquisition, and XR frames; the UI should too.

  • W3C WebXR application flow

表現・インタラクションのアイデアExpression and interaction idea

開始ボタンの押下、permission / session の解決、最初の XR frame を3色の receipt にし、frame 到着前は 2D loading を残します。拒否なら赤い failure card を短く出し、通常表示の操作をそのまま継続できる構成です。

Three receipts make activation, session resolution, and the first frame legible while keeping a 2D fallback alive.

制作に使えそうな技術メモProduction note

isSessionSupported() は session を開始しない probe、requestSession() は user activation から呼ぶ操作、XRSession.requestAnimationFrame() は session 専用の frame loop です。immersive frame の predictedDisplayTime は表示予定時刻で、レンダリング可能時間の推測には使いません。

Keep support probing, session creation, and XR frame timing in distinct fields.

サンプルデータの可能性と組み合わせSample data potential and combinations

activation / session / XR frame の時刻と失敗名は、端末別の起動成功率、展示の導入導線、業務端末の fallback copy、QA の再現ログに再利用できます。次段階では hand input や layer redraw、GPU queue completion を同じ session ID に紐づけ、画面録画や thermal telemetry と照合できます。

Activation and frame receipts can feed device rollout, UX fallback, and QA logs.
