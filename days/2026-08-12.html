今日の重要トピックKey topics today

  1. W3C WebXR Hit Test Module は `requestHitTestSource()`、`getHitTestResults()`、`XRHitTestTrackableType` の `point` / `plane` / `mesh` を定義し、hit test source の作り過ぎを privacy measure として拒否できるとしている。 The W3C WebXR Hit Test Module defines `requestHitTestSource()`, `getHitTestResults()`, and `XRHitTestTrackableType` values `point`, `plane`, and `mesh`, and allows user agents to reject excessive hit-test source requests as a privacy measure.
  2. Immersive Web の Hit Test with Anchors sample は viewer space から hit test source を作り、毎フレーム reticle を更新し、select 時に `XRHitTestResult.createAnchor()` へ進む最小の実装例として参照しやすい。 The Immersive Web Hit Test with Anchors sample is a compact reference for creating a hit-test source from viewer space, updating a reticle every frame, and calling `XRHitTestResult.createAnchor()` on select.
  3. WebXR Anchors Module は `XRHitTestResult.createAnchor()`、`XRFrame.createAnchor()`、persistent handle、restore / delete API を定義し、persistent anchors の map は user agent 側の上限や削除に左右される。 The WebXR Anchors Module defines `XRHitTestResult.createAnchor()`, `XRFrame.createAnchor()`, persistent handles, restore / delete APIs, and notes that persistent-anchor maps depend on user-agent limits and deletion behavior.
  4. WebXR Gamepads Module は XR input source の `gamepad` が frame ごとに live update されることを示し、保存フィードバックを作る時は前フレームとの差分をアプリ側で保持する必要がある。 The WebXR Gamepads Module shows that an XR input source `gamepad` is live-updated each frame, so apps need their own cached state when deriving save feedback from input changes.
  5. Gamepad / haptics は利用できない環境も多いため、今日のサンプルでは実 actuator があれば `pulse()` を試し、なければ視覚ログとして同じ feedback decision を残す。 Gamepad haptics are not broadly available, so today's sample attempts `pulse()` when an actuator exists and otherwise keeps the same feedback decision visible in the log.

注目事例と何が面白いかNotable example and why it matters

今日の注目は、Immersive Web の Hit Test with Anchors sample が示す `viewer` space -> `requestHitTestSource()` -> `frame.getHitTestResults()` -> reticle -> `createAnchor()` の流れです。この流れは実装の入口として明快ですが、実サービスでは一回の結果だけで保存すると、pose jitter、trackable type の違い、anchor quota、privacy trim、ユーザーへの保存 feedback が抜け落ちます。そこで今日の自作サンプルでは、複数フレームの履歴を先に可視化し、保存判断と haptic / audio 相当の feedback を同じ decision として扱いました。

Today's notable reference is the Immersive Web Hit Test with Anchors sample, which clearly shows the path from `viewer` space to `requestHitTestSource()`, `frame.getHitTestResults()`, reticle rendering, and `createAnchor()`. That is a good implementation entry point, but production experiences need more than one result: pose jitter, trackable type, anchor quota, privacy trimming, and user feedback all matter. Today's original sample visualizes multi-frame history first, then treats save readiness and haptic / audio-style feedback as the same decision.

表現・インタラクションのアイデアExpression and interaction idea

サンプルは canvas 上の照準をドラッグすると、擬似 `getHitTestResults()` の履歴点が揺れながら蓄積されます。History frames、Pose jitter、Surface drift を変えると安定度リングが広がり、Trackable type を `plane` / `mesh` / `point` に切り替えると保存 score が変わります。Anchor quota used を上げると `quota hold`、Privacy trim を上げると `trim + save` へ寄り、Save ボタンでは保存成功か失敗かに応じて pulse ログを出します。実 actuator が見つかれば Gamepad haptics の `pulse()` も試します。

Dragging the canvas cursor accumulates a jittering history of pseudo `getHitTestResults()` points. History frames, Pose jitter, and Surface drift change the stability ring, while switching Trackable type between `plane`, `mesh`, and `point` changes the save score. Raising Anchor quota used leads to `quota hold`; raising Privacy trim biases toward `trim + save`. Pressing Save emits pulse feedback based on success or failure, and the sample tries Gamepad haptics `pulse()` when an actuator is available.

制作に使えそうな技術メモProduction note

実装時は `requestSession('immersive-ar', { requiredFeatures: ['hit-test'], optionalFeatures: ['anchors'] })` のように feature を明示し、`viewer` space で hit test source を作ってから、XR frame loop 内で `getHitTestResults()` の先頭結果だけでなく、数フレーム分の pose spread、normal の変化、trackable type、滞在時間を保存 score にします。`createAnchor()` の前に quota / persistent handle の扱いを UI に出し、保存成功時は `XRInputSource.gamepad` 由来の actuator があれば pulse、なければ音・色・ログで同じ feedback を返す設計が扱いやすいです。

For implementation, request features explicitly, for example `requestSession('immersive-ar', { requiredFeatures: ['hit-test'], optionalFeatures: ['anchors'] })`, create a hit-test source from `viewer` space, and in the XR frame loop compute a save score from several frames of pose spread, normal changes, trackable type, and dwell time instead of only the first `getHitTestResults()` result. Before `createAnchor()`, show quota / persistent-handle state in the UI. On successful saving, pulse an actuator from `XRInputSource.gamepad` when available, and otherwise provide the same feedback through sound, color, and logs.
