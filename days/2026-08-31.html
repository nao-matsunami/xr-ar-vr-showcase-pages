今日の重要トピックKey topics today

  1. WebXR Device API の `XRInputSourceEvent` は `inputSource` と event-time の `XRFrame` を持ち、target ray pose を `getPose()` で読む入口になります。 The WebXR Device API's `XRInputSourceEvent` carries an `inputSource` and an event-time `XRFrame`, which is the entry point for reading target-ray pose via `getPose()`.
  2. MDN は event frame では `getViewerPose()` ではなく `getPose()` を使う点を明記しており、入力イベントを pose 台帳化する際の重要な制約です。 MDN explicitly notes that event frames use `getPose()` rather than `getViewerPose()`, an important constraint for turning input events into a pose ledger.
  3. WebXR Gamepads Module は `gamepad` 状態が XRSession の animation frame / event callback のまとまりで安定する前提を示しており、event と poll の照合に向いています。 The WebXR Gamepads Module describes gamepad state as stable across XRSession animation-frame or event-callback batches, making it useful for reconciling events with polling.
  4. Immersive Web Samples の Input Selection と Controller State は、select event と gamepad poll を分けて見る公式デモとして、今日の自作サンプルの比較対象になります。 Immersive Web's Input Selection and Controller State samples are official references that show select events and gamepad polling separately.
  5. 今日の公開カードは外部デモではなく、このワークスペース内の `XR Event Pose Ledger` と `Action Commit Window Replayer` の2本です。 Today's public cards focus on the original workspace samples, `XR Event Pose Ledger` and `Action Commit Window Replayer`, not external demos.

注目事例と何が面白いかNotable example and why it matters

今日の注目は、Input Selection が扱う select event と Controller State が扱う gamepad poll を、別々の機能として終わらせず、ひとつの操作台帳へ結合することです。面白い点は、event は意図の節目、frame poll は連続状態、event frame の pose はその中間にあるため、3つを同時に見ると `commit`、`hold`、`retry`、`drop` の説明が作りやすいことです。

Today's notable angle is joining the select events shown by Input Selection and the gamepad polling shown by Controller State into one action ledger rather than treating them as separate features. Events mark intent boundaries, frame polling captures continuous state, and event-frame pose sits between them, so viewing all three together makes `commit`, `hold`, `retry`, and `drop` decisions easier to explain.

制作に使えそうな技術メモProduction note

`XRInputSourceEvent.frame` は event が起きた時点の `XRFrame` で、event frame からは target ray や grip の pose を `getPose()` で取る設計に寄せるのがよいです。一方、button / axis は `XRInputSource.gamepad` を animation frame 側で読むため、実装では event timestamp、近傍 frame timestamp、pose availability、button snapshot を同じ row に保存してから dispatch 判定を行うと、二重発火や stale pose を後から検証できます。

`XRInputSourceEvent.frame` is the `XRFrame` for the time when the event occurred, so event handling should read target-ray or grip pose through `getPose()`. Button and axis values are usually read from `XRInputSource.gamepad` on the animation-frame side, so implementations should store event timestamp, nearby frame timestamp, pose availability, and button snapshots in one row before dispatching decisions, making duplicate firing and stale pose easier to inspect later.
