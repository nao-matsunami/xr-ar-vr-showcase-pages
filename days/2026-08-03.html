今日の重要トピックKey topics today

  1. WebXR Body Tracking Module Level 1 は 2025-09-05 の Draft Community Group Report で、`body-tracking` feature descriptor と `XRFrame.body` を定義している。 The WebXR Body Tracking Module Level 1 Draft Community Group Report dated 2025-09-05 defines the `body-tracking` feature descriptor and `XRFrame.body`.
  2. Body Tracking では `XRBody` が body joints の ordered map として扱われ、仕様上の `size` は 83 とされているため、手だけでなく hips、spine、head、legs まで含む入力面として考える必要がある。 Body Tracking represents `XRBody` as an ordered map of body joints with a specified `size` of 83, so the input surface includes hips, spine, head, and legs as well as hands.
  3. 同仕様は privacy risk を強く扱い、session 作成時の explicit consent、個人識別につながる高精度 body data の匿名化、`inline` session での非対応を要求している。 The specification treats privacy risk directly, requiring explicit consent at session creation, anonymization of body data that could identify users, and no support in `inline` sessions.
  4. 部分遮蔽時は個別 joint だけを欠損させるのではなく、UA が obscured joints を emulate するか、全 joint pose を null にするという設計が示されている。 For partial occlusion, the design is not per-joint dropout; the UA should emulate obscured joints or report null poses for all joints.
  5. 公式デモ一覧は引き続き参考リンクに留め、今日の公開カードは body stream をアプリ側でどう絞るかを触れる自作サンプルに限定した。 Official demo indexes remain reference links only, while today's public card focuses on the original sample for constraining body streams at the app boundary.

注目事例と何が面白いかNotable example and why it matters

今日の注目は、WebXR Body Tracking Module が full-body avatar だけでなく、privacy boundary の設計課題を前面に出している点です。`XRFrame.body` で 83 joint の pose を扱えるということは、動きの癖、体格、姿勢、身体可動域が継続的な入力データになるということでもあります。仕様の privacy section は、同意、匿名化、`inline` session 不可、遮蔽時の all-or-emulated 方針まで踏み込んでおり、アプリ側でも「取得できたものを全部 UI に流す」のではなく、公開レベルを明示的に絞る設計が必要だと分かります。

Today's notable point is that the WebXR Body Tracking Module foregrounds privacy-boundary design, not just full-body avatars. If `XRFrame.body` can expose poses for 83 joints, then motion habits, body shape, posture, and range of movement become continuous input data. The privacy section covers consent, anonymization, no `inline` support, and all-null-or-emulated handling under occlusion, which suggests applications should deliberately limit publish levels instead of forwarding every available pose into UI logic.

表現・インタラクションのアイデアExpression and interaction idea

今日のサンプルでは、赤い raw skeleton と水色または黄色の公開 pose を重ねて表示します。Consent を切ると `XRFrame.body` が null になる想定に切り替わり、Occlusion を上げると emulate か all-null のどちらかに分岐します。Rounding granularity は joint を個別にノイズ化するのではなく、静的 body model へ丸めるという考え方を可視化し、Retention window と Motion velocity は、ログを長く保持するほど・動きが細かいほど privacy risk が上がることを示します。

The sample overlays a red raw skeleton with a cyan or amber public pose. Turning consent off switches to an `XRFrame.body`-style null output, and increasing occlusion routes to either emulation or all-null behavior. Rounding granularity visualizes mapping to a coarse static body model instead of independently noising each joint, while retention window and motion velocity show how longer logs and more detailed motion raise privacy risk.

制作に使えそうな技術メモProduction note

実装では `requiredFeatures: ["body-tracking"]` を本当に要求する前に、UI 上で何を公開するかを決める policy layer を分けておくとよさそうです。アプリの内部 pose、network 送信 pose、録画・解析用 pose、画面表示用 pose を同じ object で扱わず、consent、session mode、occlusion、rounding、retention、feature purpose を別々の gate にします。遮蔽時の挙動も「欠けた joint だけ消す」と骨格が誤解されるので、静的 model への degrade か all-null のどちらかを明示した方が安全です。

A production implementation should separate a policy layer before actually requesting `requiredFeatures: ["body-tracking"]`. Internal poses, network poses, recorded analysis poses, and display poses should not share one object without constraints; consent, session mode, occlusion, rounding, retention, and feature purpose should be separate gates. Under occlusion, simply hiding individual joints can misrepresent the body, so explicit degradation to a static model or all-null output is safer.

サンプルデータの可能性と組み合わせSample data potential and combinations

このサンプルからは、公開 joint 数、emulated joint 数、privacy risk、k-anonymity 風の粗さ、遮蔽率、保持時間、publish state の履歴が取れます。これを実機の body / hand tracking log、運動フォーム動画、アバター retargeting、空間音響、展示会場の匿名人数カウント、GLSL の body aura 表現、AI による姿勢分類と組み合わせると、体験表現とプライバシー制約を同じ画面で比較できます。業務用途では、トレーニング記録、遠隔支援、VR 会議 avatar、店舗内 AR 誘導のデータ最小化レビューに展開できます。

The sample yields publish-state history, exposed joint count, emulated joint count, privacy risk, k-anonymity-like coarseness, occlusion, and retention. Combining those with real device body/hand tracking logs, exercise videos, avatar retargeting, spatial audio, anonymous installation counting, GLSL body-aura visuals, or AI posture classification would let teams compare expression and privacy constraints in one view. Client-facing uses include training records, remote support, VR meeting avatars, and data-minimization reviews for in-store AR guidance.

試すならこれIf you try one thing

サンプルを開き、まず Consent を off にして全 readout が null 側へ倒れることを見てください。次に Consent を戻し、Occlusion を 70% 以上へ上げ、Emulate toggle を切り替えると、仕様で示されている「emulate するか、全 joint pose を null にするか」の違いが見えます。最後に Rounding を上げると、raw skeleton と公開 pose の差が広がり、体格・動作の細部を落とす効果が分かります。

Open the sample and first turn consent off to see the readouts collapse toward null. Then restore consent, raise occlusion above 70%, and switch the emulation toggle to compare the spec-shaped choice between emulating obscured joints and making all joint poses null. Finally raise rounding to see the gap between the raw skeleton and public pose, showing how body and motion detail can be reduced.
