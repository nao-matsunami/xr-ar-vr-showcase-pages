今日の重要トピックKey topics today

  1. WebXR Anchors Module は `requestPersistentHandle()`、`persistentAnchors`、`restorePersistentAnchor(uuid)`、`deletePersistentAnchor(uuid)` を定義し、persistent anchor は origin ごとの map として扱われる。 The WebXR Anchors Module defines `requestPersistentHandle()`, `persistentAnchors`, `restorePersistentAnchor(uuid)`, and `deletePersistentAnchor(uuid)`, with persistent anchors modeled as an origin-scoped map.
  2. 仕様上、persistent anchor の保存 map のサイズは UA が決め、UA は上限やその他の理由で entry を削除できるため、復元失敗は通常経路として扱う必要がある。 The specification leaves persistent-anchor map size to the user agent and allows entries to be removed for capacity or other reasons, so restore failure should be treated as a normal route.
  3. Plane Detection Module は `XRFrame.detectedPlanes`、`XRPlane.polygon`、`orientation`、`semanticLabel`、`initiateRoomCapture()` を定義し、復元失敗後の再配置候補として使いやすい。 The WebXR Plane Detection Module defines `XRFrame.detectedPlanes`, `XRPlane.polygon`, `orientation`, `semanticLabel`, and `initiateRoomCapture()`, which are useful for recovery placement candidates.
  4. Plane Detection の privacy guidance は plane polygon の detail reduction や小さすぎる plane の除外に触れており、復旧ログにも raw geometry を残しすぎない設計が重要になる。 Plane Detection privacy guidance discusses polygon detail reduction and ignoring overly small planes, so recovery logs should avoid retaining raw geometry.
  5. WebXR Hand Input Module は articulated hand poses を WebXR に追加するため、anchor 復旧時の微調整 UI を controller 前提にしない選択肢として使える。 The WebXR Hand Input Module adds articulated hand poses to WebXR, making hand-based fine adjustment a viable alternative to controller-only recovery.

注目事例と何が面白いかNotable example and why it matters

今日の注目は、persistent anchor を「保存できたら終わり」ではなく、翌セッションで戻らない、上限で消える、環境が変わる、手で少し合わせ直す、という運用の失敗回復まで含めて UI にする点です。Anchors 仕様では persistent anchor の map は UA 管理で、保存数の上限や削除があり得ます。Plane Detection の room capture と semanticLabel は再配置候補を作るのに便利ですが、復旧時にも raw polygon を保存しすぎない判断が必要です。今日のサンプルは公式デモを外部カードにせず、これらの状態を canvas 上の自作判断盤としてまとめました。

Today's notable point is treating persistent anchors not as finished once saved, but as an operational recovery problem: they may fail to restore in a later session, be removed because of capacity, become stale when the room changes, or need hand-based fine adjustment. In the Anchors spec, the persistent-anchor map is user-agent managed and may have limits or deletions. Plane Detection room capture and semantic labels are useful for recovery candidates, while recovery still needs to avoid retaining raw polygon data. The public card is the original canvas decision board rather than an external demo.

表現・インタラクションのアイデアExpression and interaction idea

サンプルは保存済み anchor を光るノードとして表示し、Restore、Recalibrate、Delete low、Add anchor を切り替える復旧ラボです。Tracking confidence、Room change、Anchor quota、Hand correction を動かすと、復元率、quota 使用量、補正距離、削除候補、fallback が変化します。canvas をドラッグすると手入力の補正点が動き、近くの anchor だけが少し寄るため、復元失敗後にユーザーへ全面再スキャンを強制せず、局所的に直す体験を試せます。

The sample shows saved anchors as luminous nodes and exposes Restore, Recalibrate, Delete low, and Add anchor actions. Changing tracking confidence, room change, anchor quota, and hand correction updates restore rate, quota usage, correction distance, deletion target, and fallback. Dragging the canvas moves the hand-correction point, nudging only nearby anchors, which tests local recovery instead of forcing a full rescan after every restore failure.

制作に使えそうな技術メモProduction note

実装では `requestPersistentHandle()` で得た UUID を保存し、次回 `session.persistentAnchors` と照合して `restorePersistentAnchor(uuid)` を順に試す構成にします。失敗時は `deletePersistentAnchor(uuid)`、新規 hit test / plane anchor、または hand input による nudge を分岐にします。保存ログは UUID、粗い pose band、semantic label、復元スコア、retry 回数、削除理由に留め、plane polygon や camera frame は残さないのが扱いやすいです。quota は UI 上で可視化し、低優先度 anchor を先に消す判断をユーザーに説明できるようにします。

A practical implementation can save UUIDs returned by `requestPersistentHandle()`, compare them with `session.persistentAnchors` on the next session, and try `restorePersistentAnchor(uuid)` in order. Failures branch to `deletePersistentAnchor(uuid)`, new hit-test or plane anchors, or a hand-input nudge. Logs should keep UUIDs, coarse pose bands, semantic labels, restore score, retry count, and deletion reason, while avoiding plane polygons or camera frames. Quota should be visible so users understand why lower-priority anchors are deleted first.

サンプルデータの可能性と組み合わせSample data potential and combinations

今日のサンプルからは、復元率、anchor ごとの priority、drift、age、restore score、quota 使用量、削除候補、手入力補正量、fallback 種別を取れます。展示運用の設営チェックリスト、店舗棚の販促 UI、建築注釈、CMS の配置版管理、AI による失敗原因分類、音や haptics の復旧通知と組み合わせると、単なる AR 配置ではなく「戻らなかった時にどう直すか」を運用データとして育てられます。複数日の depth / mesh / plane / camera consent ladder と結ぶと、最小露出の復旧ルート選択にも使えます。

Today's sample yields restore rate, per-anchor priority, drift, age, restore score, quota usage, deletion target, hand-correction amount, and fallback type. Combined with exhibition setup checklists, retail shelf promotion UI, architectural annotations, CMS placement versions, AI failure-cause classification, or audio/haptic recovery cues, it turns AR placement into operational data about how to recover when placement does not return. Connecting it with recent depth / mesh / plane / camera-consent samples can support lowest-exposure recovery routing.

The selected prototype is `Anchor Restore Recovery Lab`. Useful additions would be a real `navigator.xr.isSessionSupported("immersive-ar")` probe, CSV export of simulated restore logs, failure-reason classification, multi-operator setup conflict display, and audio or haptic recovery guidance.
