今日の重要トピックKey topics today

  1. WebXR の XRView.requestViewportScale() は 0 より大きい値を要求でき、1 を超える値は 1 に丸められる。 XRView.requestViewportScale() requests a positive scale and clamps values above one.
  2. 同一フレームでは requestViewportScale() の後に最初の getViewport() を呼ぶと、そのフレームの scaled viewport が確定する。 The first getViewport() after a request applies the scaled viewport for that frame.
  3. recommendedViewportScale は null になり得るため、値があることや端末が要求を受理することを前提にできない。 recommendedViewportScale may be null and requests may be ignored.
  4. 推奨値は量子化とヒステリシスで安定化でき、頻繁な品質揺れを避ける助けになる。 Quantization and hysteresis can prevent distracting quality oscillation.
  5. 縮尺低下は中央 HUD や重要な文字まで粗くする合図ではなく、背景・粒子・遠景から品質を落とす契機として扱う。 Scale reduction should protect central HUD text and reduce peripheral detail first.

注目事例と何が面白いかNotable example and why it matters

W3C WebXR Device API は、XRView ごとに requestViewportScale() で描画領域の縮尺を要求し、続く最初の getViewport() でそのフレームの viewport を確定する順序を定義します。公式 Viewport Scaling sample は API の入口として有用ですが、公開アーカイブの中心は外部デモではなく自作の判断実験です。本命では軽量、重い shader、UA 推奨、順序ミスを切り替え、要求された値と実際に適用された値を一緒に表示します。

The main prototype makes frame ordering and requested-versus-applied scale visible.

表現・インタラクションのアイデアExpression and interaction idea

本命は viewport の内側に背景 detail を置き、中央の HUD text を別の優先対象として残します。順序ミスでは request があってもそのフレームの viewport は 1.00 のままと表示し、成功を偽装しません。派生では 0.98 / 0.78 / 0.74 / 0.58 と null のヒントを操作し、1.00 / 0.84 / 0.68 の3段へ丸めます。近い値は hold し、画質の呼吸のような揺れを避けます。

The main protects HUD readability; the derivative stabilizes changing recommendations into three tiers.

制作に使えそうな技術メモProduction note

実装では XRFrame 内で pose.views を走査し、view.requestViewportScale?.(desiredScale) を getViewport(view) の前に呼びます。recommendedViewportScale は null なら requestViewportScale(null) が無効なので、独自 heuristic または scene complexity の品質階段に落とします。getViewport() が返した幅・高さはそのフレームの実証として記録し、要求値だけで成功判定しません。API が無い、または縮尺が変化しない端末では、ポスト処理、粒子、遠景、影の順に負荷を下げます。

Request before getViewport, measure returned dimensions, and use a content-quality ladder when the API is absent or ignored.

サンプルデータの可能性と組み合わせSample data potential and combinations

2本から再利用できるのは requested scale、返却 viewport、推奨値、採用 tier、hold 理由、保護したコンテンツという小さな receipt です。GPU timer、WebGPU の pass 時間、音声のビート、視線や手の操作密度と組み合わせれば、派手な効果を落としても会話・字幕・作業手順を保つ XR 品質調整にできます。生の視線や身体データを保存せず、最終判断だけを保存する設計にも向きます。

Compact scale receipts can join GPU timing, audio, or interaction density without retaining raw biometric traces.

俯瞰メモBird's-eye memo

XR の品質調整は「画質を落とす」一つのレバーではありません。縮尺を変える操作、いつ適用されたか、どの内容を読みやすく残すか、縮尺が使えない時に何を削るかを分けて初めて、端末差の大きい WebXR でも説明可能になります。特に頻繁な品質の往復は快適さを壊し得るため、変化を少数の意味ある段階へ丸める設計が重要です。

Quality adaptation becomes trustworthy when application timing, content priority, and fallback are explicit.
