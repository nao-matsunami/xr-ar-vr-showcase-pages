今日の重要トピックKey topics today

  1. W3C Gamepad API は haptic actuator、supported effect、`playEffect()`、`reset()` を一般モデルとして定義し、XR controller の触覚 cue を queue 化する土台になります。 The W3C Gamepad API defines haptic actuators, supported effects, `playEffect()`, and `reset()` as a general model, forming a base for queued XR controller haptic cues.
  2. MDN の `GamepadHapticActuator.pulse()` は限定対応ながら、強度と duration を渡す旧来 fallback として読みやすく、重複 call が進行中の pulse を上書きする注意点も示しています。 MDN's `GamepadHapticActuator.pulse()` is limited in support but useful as a clear legacy fallback that accepts intensity and duration, with the important caveat that repeated calls override an in-progress pulse.
  3. WebXR Gamepads Module は XRInputSource の gamepad mapping を XR controller 向けに扱うための前提で、昨日の frame poller から今日の haptic queue へ接続しやすい。 The WebXR Gamepads Module gives the XR-controller-specific mapping assumptions needed to connect yesterday's frame poller to today's haptic queue.
  4. Immersive Web の Controller State / Input Profiles サンプルは、実機 input source の buttons / axes / profiles を frame loop で見る検証入口として有用です。 Immersive Web's Controller State and Input Profiles samples are useful entry points for inspecting real input-source buttons, axes, and profiles inside the frame loop.
  5. WebXR Input Profiles の motion-controllers package は raw button index ではなく conceptual component として trigger / squeeze / thumbstick を扱う設計を後押しします。 The WebXR Input Profiles motion-controllers package encourages handling trigger, squeeze, and thumbstick as conceptual components rather than raw button indices.

注目事例と何が面白いかNotable example and why it matters

今日の注目は、Gamepad API の haptic actuator モデルと Immersive Web Samples の Controller State / Input Profiles です。XR controller では select / squeeze の単発 event だけでなく、trigger value、squeeze value、axis、handedness、profile、触覚 actuator の可用性が同時に問題になります。面白い点は、入力を直接 UI 状態へ渡すのではなく、semantic action、priority、cooldown、左右別 queue に分けると、保存成功、拒否、警告、移動 nudge のような cue を衝突させずに整理できるところです。

Today's notable references are the Gamepad API haptic actuator model and Immersive Web's Controller State / Input Profiles samples. XR controllers require more than one-shot select / squeeze events: trigger value, squeeze value, axes, handedness, profile, and haptic actuator availability all matter together. The interesting part is that routing input through semantic actions, priority, cooldown, and separate left/right queues makes save success, rejection, warning, and movement nudge cues manageable without uncontrolled conflicts.

表現・インタラクションのアイデアExpression and interaction idea

サンプルでは trigger、squeeze、thumbstick y、warning priority を動かし、`select`、`grab`、`warn`、`nudge`、`idle` に分類します。dominant hand に照準線を出し、左右 controller の queue と active pulse を canvas 上で可視化します。`warn` は左右へ mirror dispatch し、`select` や `grab` は dominant hand のみに流すため、同じ入力 adapter から触覚の局所性と全体警告の違いを試せます。

The sample maps trigger, squeeze, thumbstick y, and warning priority into `select`, `grab`, `warn`, `nudge`, or `idle`. It draws an aim ray from the dominant hand and visualizes each controller's queue plus active pulse on canvas. `warn` mirrors to both hands, while `select` and `grab` stay on the dominant hand, so one input adapter can demonstrate the difference between local tactile feedback and global alerts.

制作に使えそうな技術メモProduction note

実装では XR frame callback 内で `inputSource.gamepad` を読み、Input Profiles で conceptual component に寄せ、semantic action payload を作ります。haptics 側は `gamepad.vibrationActuator.playEffect()` があれば優先し、なければ `gamepad.hapticActuators[0].pulse()`、それもなければ Web Audio / visual cue へ落とすとテストしやすいです。Gamepad API の仕様上、効果の preempt、hidden document、NotSupportedError、supported effects の差を前提に、duration、priority、cooldown、actuator budget を adapter で吸収します。

In production, read `inputSource.gamepad` inside the XR frame callback, use Input Profiles to map raw data to conceptual components, and emit semantic action payloads. The haptics layer can prefer `gamepad.vibrationActuator.playEffect()`, fall back to `gamepad.hapticActuators[0].pulse()`, then to Web Audio / visual cues for testing. Given the Gamepad API model, preemption, hidden documents, NotSupportedError, and supported-effect differences should be absorbed by adapter-level duration, priority, cooldown, and actuator-budget rules.
