今日の重要トピックKey topics today

  1. WebXR Device API の最新公開版は 2026-06-09 の Candidate Recommendation Draft で、入力イベント、XRFrame、visibility state の基礎を確認できます。 The latest published WebXR Device API is the 2026-06-09 Candidate Recommendation Draft, covering input events, XRFrame, and visibility-state foundations.
  2. MDN の XRInputSourceEvent は event frame では getViewerPose ではなく getPose を使う点を明示しており、入力時点の pose 保存設計に直結します。 MDN's XRInputSourceEvent documentation clarifies that event frames use getPose rather than getViewerPose, which directly informs pose-at-input logging.
  3. WebXR Gamepads Module は XRInputSource.gamepad が frame ごとに同じ object 上で更新されるため、比較には数値 snapshot の保存が必要だと説明しています。 The WebXR Gamepads Module explains that XRInputSource.gamepad is updated in place each frame, so comparisons require stored numeric snapshots.
  4. XRSession.visibilityState の visible-blurred / hidden は frame と input 処理の前提を変えるため、commit 判定 policy の主要な軸になります。 XRSession.visibilityState values such as visible-blurred and hidden change assumptions for frames and input processing, making them key axes in commit policy.
  5. 今日の公開カードは外部デモではなく、このワークスペース内の `XR Input Policy Comparator` と `XR Pose Gap Patch Router` の2本です。 Today's public cards focus on the original workspace samples, `XR Input Policy Comparator` and `XR Pose Gap Patch Router`, not external demos.

注目事例と何が面白いかNotable example and why it matters

注目したのは、公式サンプルが示す select event と controller gamepad state を、単なる実装例ではなく、あとから policy を差し替えられる検証ログとして扱うことです。同じ入力でも strict では drop、forgiving では commit になる行があり、誤操作を防ぐ設計と、取りこぼしを減らす設計の差分を UI で見られる点が面白いです。

The notable angle is treating select events and controller gamepad state from the official samples as replayable validation logs rather than isolated implementation examples. The same input row can become drop under strict policy and commit under forgiving policy, making the tradeoff between preventing false actions and reducing missed actions visible in the UI.

表現・インタラクションのアイデアExpression and interaction idea

本命サンプル `XR Input Policy Comparator` は、保存済み風の XR 入力 row を読み込み、strict / balanced / forgiving の verdict を横並びで表示します。Policy bias を動かすと commit window、gamepad age、confidence 閾値が変わり、何件の verdict が flip したかを確認できます。派生サンプル `XR Pose Gap Patch Router` は、event-frame pose が欠けた時に last pose と gamepad snapshot で patch できるかを、reticle と段階判定で確認します。

The main sample, `XR Input Policy Comparator`, loads saved-style XR input rows and displays verdicts for strict, balanced, and forgiving policies side by side. Moving Policy bias changes the commit window, gamepad age, and confidence threshold, then shows how many verdicts flip. The derivative sample, `XR Pose Gap Patch Router`, checks whether missing event-frame pose can be patched with the last pose and gamepad snapshot, visualized through a reticle and staged checks.

制作に使えそうな技術メモProduction note

実機版では `selectstart` / `select` / `squeeze` の `XRInputSourceEvent.frame` から target ray pose を読み、近傍 animation frame の `XRInputSource.gamepad` 数値を同じ row に保存します。Gamepad object は live 更新なので参照保持ではなく buttons / axes の値だけを保存します。`visibilityState` が `visible-blurred` または `hidden` の時は、pose confidence だけで commit せず、policy 側で hold / drop を明示したほうが検証しやすいです。

A device-backed version should read target-ray pose from `XRInputSourceEvent.frame` during `selectstart`, `select`, and `squeeze`, then store nearby animation-frame `XRInputSource.gamepad` numbers in the same row. Because the Gamepad object is live, persist button and axis values rather than object references. When `visibilityState` is `visible-blurred` or `hidden`, avoid committing from pose confidence alone; make hold/drop explicit in policy for easier validation.
