今日の重要トピックKey topics today

  1. WebXR Raw Camera Access Module は 2025-12-11 の Draft Community Group Report で、`camera-access` feature descriptor、`XRView.camera`、`XRWebGLBinding.getCameraImage()` を定義している。 The WebXR Raw Camera Access Module Draft Community Group Report dated 2025-12-11 defines the `camera-access` feature descriptor, `XRView.camera`, and `XRWebGLBinding.getCameraImage()`.
  2. `camera-access` は `immersive-ar` の背後に表示される camera image pixels をアプリが直接扱える強力な機能で、仕様上も現在の WebXR 能力の中で最も privacy implication が高いと説明されている。 `camera-access` lets applications directly handle camera image pixels behind an `immersive-ar` session, and the spec describes it as having the highest privacy implications among current WebXR capabilities.
  3. Raw Camera Access は `xr-spatial-tracking` だけでなく `camera` permissions policy も必要で、inline XR device はこの機能を support 可能な device として扱ってはいけない。 Raw Camera Access requires both `xr-spatial-tracking` and `camera` permissions policy, and the inline XR device must not be treated as capable of supporting the feature.
  4. XRCamera は frame の active / animationFrame 条件、view との alignment、native camera image の有無によって `null` になり得るため、アプリ側は raw texture 前提ではなく degrade path を持つ必要がある。 XRCamera can be `null` depending on frame activity, animation-frame timing, native image availability, and view alignment, so applications need a degrade path instead of assuming raw textures.
  5. 公式サンプルと proposal sample は参考リンクとして使い、今日の公開カードは raw camera request を最小化する自作 crop gate に限定した。 Official samples and proposal samples remain reference links only; today's public card is the original crop gate for minimizing raw camera requests.

注目事例と何が面白いかNotable example and why it matters

今日の注目は Raw Camera Access が、AR の pass-through 映像を「見えている背景」から「アプリが読める raw pixels」に変える点です。Hit Test や Depth Sensing は現実空間の位置や距離を借りる機能ですが、Raw Camera Access は環境そのものの画像を扱うため、同意、permissions policy、privacy indicator、view との alignment が中心課題になります。仕様は `camera-access` を不要に要求しないことを強く促しており、アプリ側でも最初から required feature にせず、semantic mask、depth fallback、no-camera mode へ落とせる設計が重要だと分かります。

Today's notable point is that Raw Camera Access turns AR passthrough from a visible background into raw pixels the app can read. Hit Test and Depth Sensing borrow real-world position or distance, but Raw Camera Access handles images of the environment itself, so consent, permissions policy, privacy indicators, and view alignment become central. The spec strongly discourages unnecessary `camera-access` requests, which suggests applications should avoid defaulting to required features and should degrade to semantic masks, depth fallback, or no-camera modes.

制作に使えそうな技術メモProduction note

実装では `requestSession("immersive-ar", { optionalFeatures: ["camera-access"] })` を基本にし、raw pixels が本当に必要なフレームだけ `XRView.camera` と `getCameraImage(camera)` を読む方針がよさそうです。`camera` permissions policy、`xr-spatial-tracking`、secure context、active XR frame、view alignment、native camera image availability を独立した gate にし、失敗時は depth sensing の coarse mask、hand / body joint の抽象 state、または DOM overlay の手動入力へ落とします。raw texture を analytics や network へ流す場合は、crop、downsample、redaction、retention window を session policy として明示します。

A production implementation should usually start with `requestSession("immersive-ar", { optionalFeatures: ["camera-access"] })` and read `XRView.camera` plus `getCameraImage(camera)` only on frames that truly need raw pixels. Treat `camera` permissions policy, `xr-spatial-tracking`, secure context, active XR frame, view alignment, and native image availability as independent gates. On failure, degrade to a coarse depth-sensing mask, abstract hand/body state, or manual DOM-overlay input. If raw textures flow into analytics or networking, crop, downsample, redaction, and retention windows should be explicit session policy.

サンプルデータの可能性と組み合わせSample data potential and combinations

このサンプルからは、露出 pixel 比率、risk score、consent、alignment、crop size、fallback state、privacy indicator の有無、event trace が取れます。実機の raw camera texture、depth map、plane / mesh detection、手入力、body tracking、AI 物体検出、展示会場の説明 overlay、倉庫や店舗の AR 作業指示と組み合わせると、どの機能が raw pixels を本当に必要としているかを比較できます。特に AI と組み合わせる場合は、raw image を直接送る前に semantic label だけで成立する体験を先に試す価値があります。

The sample produces exposed-pixel ratio, risk score, consent, alignment, crop size, fallback state, privacy-indicator state, and an event trace. Combining those with real raw camera textures, depth maps, plane or mesh detection, hand input, body tracking, AI object detection, exhibition overlays, or AR work instructions for stores and warehouses would help compare which features truly need raw pixels. When AI is involved, it is worth testing whether semantic labels alone can support the experience before sending raw images.

俯瞰メモBird's-eye memo

ここ数日の permission、input profile、controller / hand arbitration、body tracking の流れは、入力やセンサーの豊かさをどう制限して公開するかというテーマにまとまってきました。今日の Raw Camera Access はその中でも最も直接的で、現実空間の画像を扱うため、表現の前に gate design が必要です。派手な camera shader ではなく、crop、mask、fallback、indicator を先に触れるようにしたことで、今後の AI / WebGPU / mesh 系サンプルへつなげやすくなります。

The recent sequence around permissions, input profiles, controller/hand arbitration, and body tracking has converged on how to constrain rich sensor input before publishing it. Raw Camera Access is the most direct case because it handles images of the real environment, so gate design needs to precede visual effects. By making crop, mask, fallback, and indicator controls tangible before building a camera shader, this sample creates a better bridge toward AI, WebGPU, and mesh-oriented prototypes.
