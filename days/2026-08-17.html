注目事例と何が面白いかNotable example and why it matters

今日の注目は WebXR Anchors Module の「作った anchor をどう維持するか」です。`XRAnchor.anchorSpace` は描画の基準になりますが、仕様上は native anchor が一時的に locate 不能になる可能性や、追跡が戻らない可能性があります。面白いのは、anchor は一度置いたら終わりではなく、pose の drift、unlocatable frame、persistent handle、再 hit-test 候補をまとめて見ながら「そのまま表示するか、警告するか、隠して待つか、置き換えるか」を毎フレーム近い粒度で判断する UI 部品になる点です。

Today's notable point is how the WebXR Anchors Module treats maintaining anchors after creation. `XRAnchor.anchorSpace` becomes the rendering reference, but native anchors may be temporarily unlocatable or may never recover tracking. The interesting part is that an anchor is not finished once placed; it becomes a UI component that continuously weighs pose drift, unlocatable frames, persistent handles, and re-hit-test candidates to decide whether to keep rendering, warn, hide and wait, or replace it.

サンプルでは Stable table / Slow drift / Unlocatable frames / Entity moved のシナリオを切り替え、drift cm、unlocatable frames、tracking confidence、re-hit-test quality を操作します。canvas には original anchor、現在の `anchorSpace` pose、再 hit-test 候補、decision rail を描き、ドラッグで現在位置をずらせます。ユーザーに見える表現としては、急にオブジェクトを消すのではなく、keep では通常表示、warn では dim + 軽い cue、re-hit-test では候補リング、hide + wait では半透明の不確定状態を出す、といった段階的な feedback が使えます。

制作に使えそうな技術メモProduction note

実装では `XRFrame.trackedAnchors` を frame loop 内で読み、各 `XRAnchor.anchorSpace` を viewer / local / local-floor space に対して `getPose()` し、pose が取れない frame 数を anchor ごとに数えます。persistent 化する場合は `anchor.requestPersistentHandle()` を保存し、次回 session で `session.restorePersistentAnchor(uuid)` を試します。drift が閾値を超え、近傍の `getHitTestResults()` や plane / mesh 情報の品質が高い時だけ新 anchor に置き換えると、誤復旧で content が跳ねる問題を抑えられます。`delete()` 後の `anchorSpace` アクセスは InvalidStateError 前提で adapter 側に閉じ込めます。

In production, read `XRFrame.trackedAnchors` inside the frame loop, call `getPose()` for each `XRAnchor.anchorSpace` relative to viewer / local / local-floor spaces, and count unlocatable frames per anchor. For persistence, store `anchor.requestPersistentHandle()` and try `session.restorePersistentAnchor(uuid)` in the next session. Replacing with a new anchor only when drift exceeds a threshold and nearby `getHitTestResults()` or plane / mesh information is strong reduces content jumps caused by bad recovery. Access to `anchorSpace` after `delete()` should be isolated in an adapter because InvalidStateError is expected.

俯瞰メモBird's-eye memo

この流れで、AR 配置は「置く瞬間」から「置いた後の維持」へ移りました。hit-test gate は入口、anchor drift policy は運用、persistent handle は次回 session への橋渡しです。ここまでを一つの payload で扱うと、実機差や環境差が出たときに、入力、環境理解、anchor tracking、UI feedback のどこで問題が起きたかを切り分けやすくなります。

This step moves AR placement from the moment of placement into post-placement maintenance. The hit-test gate is the entrance, anchor drift policy is operations, and persistent handles bridge into later sessions. Treating all of this as one payload makes it easier to separate issues in input, environment understanding, anchor tracking, and UI feedback when device or environment differences appear.
