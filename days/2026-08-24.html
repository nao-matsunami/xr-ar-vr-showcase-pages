今日の重要トピックKey topics today

  1. W3C の WebXR Layers API Level 1 Working Draft は 2026-06-12 版で、composition layer の `destroy()` は color / depth-stencil texture 配列を空にし、GL attachment を破棄する手順として説明されています。 The W3C WebXR Layers API Level 1 Working Draft dated 2026-06-12 describes `destroy()` for composition layers as clearing color and depth-stencil texture arrays and destroying GL attachments.
  2. 同仕様の Editor's Draft は `XRMediaBinding` に `createQuadLayer()`、`createCylinderLayer()`、`createEquirectLayer()` を持たせ、HTMLVideoElement を compositor 側の media layer に接続する入口を示しています。 The Editor's Draft exposes `createQuadLayer()`, `createCylinderLayer()`, and `createEquirectLayer()` on `XRMediaBinding`, providing the entry point for connecting an HTMLVideoElement to compositor-backed media layers.
  3. Immersive Web の Layers Samples には Destroy Layer / Lifecycle と Media Layer / Basics があり、レイヤーの破棄と動画レイヤーの扱いを公式デモとして確認できます。 Immersive Web Layers Samples include Destroy Layer / Lifecycle and Media Layer / Basics, making layer destruction and video layers inspectable as official demos.
  4. MDN の `XRLayer` は secure context、experimental、limited availability とされ、現時点では production で feature detection と fallback 理由の表示が欠かせません。 MDN marks `XRLayer` as secure-context-only, experimental, and limited availability, so production code still needs feature detection and fallback reason copy.
  5. 昨日の世界固定レイヤー可読性 budget を実運用へ近づけるには、読めない layer を作らないだけでなく、古い layer を安全に外してから破棄する状態遷移が必要です。 To evolve yesterday's world-locked readability budget toward real use, the app must not only avoid unreadable layers but also remove old layers safely before destroying them.

表現・インタラクションのアイデアExpression and interaction idea

本命サンプル `Layer Lifecycle Destroy Queue` は、XR profile、composition layer 数、古い media layer 数、memory pressure、session end の状態を触ると、残す layer と破棄待ち layer がカード状に積み上がって見えます。`Process one frame` を押すと stale layer が1つ処理され、ログに renderState 更新や destroy 順の判断が残ります。派生サンプル `Media Layer Control Fallback Deck` は、equirect / cylinder / quad の形状、XRMediaBinding の有無、video readiness、decoder pressure を切り替え、media layer、projection texture、canvas fallback のどれに落とすかを大きな動画デッキとして表示します。

The main sample, `Layer Lifecycle Destroy Queue`, lets you change XR profile, composition-layer count, stale media-layer count, memory pressure, and session-end state; kept layers and queued-for-destruction layers appear as stacked cards. Pressing `Process one frame` handles one stale layer and records the render-state or destruction-order decision in the log. The derivative sample, `Media Layer Control Fallback Deck`, switches between equirect, cylinder, and quad shapes plus XRMediaBinding availability, video readiness, and decoder pressure, then displays whether playback should use a media layer, projection texture, or canvas fallback.

制作に使えそうな技術メモProduction note

実装では、古い composition layer を `session.updateRenderState({ layers: nextLayers })` から外してから `layer.destroy()` に進む順を明示し、media layer の動画差し替え時も新 layer の準備完了後に旧 layer を queue へ入れるのが扱いやすいです。`XRMediaBinding` がある場合は HTMLVideoElement を直接 media layer 化できますが、無い場合は `XRWebGLBinding` / projection layer の texture 更新、さらに無ければ通常 canvas と DOM controls に縮退します。MDN が示す通り `XRLayer` は limited availability なので、`"XRMediaBinding" in window`、`"XRWebGLBinding" in window`、`navigator.xr?.isSessionSupported()` を分けて記録すると後日の実機差分を追いやすくなります。

In production code, make the ordering explicit: remove an old composition layer from `session.updateRenderState({ layers: nextLayers })`, then call `layer.destroy()`. For media replacement, it is easier to prepare the new layer first, then enqueue the previous layer for cleanup. When `XRMediaBinding` is available, an HTMLVideoElement can feed a media layer directly; otherwise, fall back to `XRWebGLBinding` / projection-layer texture updates, then to normal canvas and DOM controls. Since MDN marks `XRLayer` as limited availability, logging `"XRMediaBinding" in window`, `"XRWebGLBinding" in window`, and `navigator.xr?.isSessionSupported()` separately will make later device comparisons easier.

俯瞰メモBird's-eye memo

ここ数日の流れは feature negotiation、bounded reference space、world-locked layer 可読性、haptic verdict と進んできました。今日の lifecycle は、それらの判定が「古い表示をどう外すか」に到達した段階です。XR では表示を作る API だけでなく、支えられない表示を安全に外して理由を伝える設計が体験品質を左右します。小さな queue と fallback reason を持つだけで、後から実機ログ、DOM Overlay、haptics、analytics に接続しやすくなります。

Recent work moved through feature negotiation, bounded reference spaces, world-locked layer readability, and haptic verdicts. Today's lifecycle sample is the point where those verdicts reach the question of how old presentation should be removed. In XR, experience quality depends not only on APIs that create display surfaces but also on safely removing unsupported surfaces and explaining why. A small queue plus fallback reason makes later connections to device logs, DOM Overlay, haptics, and analytics easier.
