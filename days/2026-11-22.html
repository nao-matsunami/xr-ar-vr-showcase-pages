今日の重要トピックKey topics today

  1. WebXR は inline、immersive-vr、immersive-ar の session mode を持ち、開始前に isSessionSupported() で可用性を確かめられる。 WebXR offers inline, immersive-vr, and immersive-ar modes and exposes session support checks.
  2. requestSession() の requiredFeatures は満たせないと session 自体を拒否し得るため、目的に不要な能力を必須にしない設計が重要になる。 Unmet required features can reject a session, so requirements should be deliberately minimal.
  3. WebXR は controller、追跡された手、視線を input source として扱い、表示と入力経路を能力に応じて切り替えられる。 Controllers, tracked hands, and gaze can be distinct XR input sources.
  4. WebXR はレンダリング技術ではなく、追跡と session を扱う API なので、scene と fallback の責任はアプリ側に残る。 WebXR manages sessions and tracking, leaving scene and fallback design to the app.

注目事例と何が面白いかNotable example and why it matters

MDN の lifecycle と requestSession() の一次ドキュメントは、session mode を調べ、利用者の操作から session を要求し、終了も扱う一連の流れを示します。面白いのは、support の確認と feature の要求が別の判断である点です。mode が使えても、不要に多い requiredFeatures が session を入口で閉じてしまいます。Immersive Web の説明どおり、WebXR は能力を対象にする API なので、体験側は能力の組み合わせを設計できます。

Mode availability and feature negotiation are separate choices; the app should preserve a useful route when optional capabilities vary.

表現・インタラクションのアイデアExpression and interaction idea

本命 Feature Ladder Studio は hand-tracking、hit-test、depth-sensing を段ごとに置き、欲しい能力・取れた能力・採用した route を分けて見せます。派生 Input Handoff Constellation は、同じ select intent を hand、controller、gaze のどれが受けたかを星と receipt に変換します。入力が欠けても意図を勝手に実行せず、利用可能な経路へ明示的に手渡す表現です。

The main separates desire, availability, and route; the derivative visualizes which input receives an explicit select intent.

制作に使えそうな技術メモProduction note

最初に navigator.xr の有無を確認し、isSessionSupported() で mode ごとの入口を決めます。requestSession() はユーザー操作から呼び、local など本当に必要な reference space のみを requiredFeatures に入れます。hand-tracking、hit-test、depth-sensing は対応機器差が大きいため optionalFeatures とし、得られた session.enabledFeatures、inputSources、frame の値をその frame で評価します。fallback は同じ意図を保ち、入力 UI と説明だけを能力に合わせて変えます。

Probe modes first, request only necessary required features, and evaluate optional capabilities on live session/frame values.

サンプルデータの可能性と組み合わせSample data potential and combinations

保存するなら座標やカメラ映像ではなく、requested/available/selected route、handoff 回数、確定までの時間だけで足ります。展示ではライトや音のレイヤーを route に連動させ、業務支援では「手で確認」「controller で確定」のような操作説明へ、教育では capabilities の変化を小さなクイズへつなげられます。

Small capability and handoff receipts can connect to installation cues, operational guidance, and education without retaining spatial data.

俯瞰メモBird's-eye memo

対応能力の違いは XR 体験の例外ではなく前提です。最上位の表現を要求することと、そこへ入れない利用者を置き去りにすることは別です。能力の不足を“失敗”として隠すより、現在の route を読める形にすると、利用者は何ができ、何を待つ必要があるかを理解できます。

Capability variation is normal in XR. Legible routes build trust better than concealing unavailable features.
