今日の重要トピックKey topics today

  1. WebXR Device API は、`requiredFeatures` の未認識・未対応・ユーザー意図不足を `XRSession` 作成失敗の条件として扱い、`optionalFeatures` は未認識なら無視、未対応でもセッション作成をブロックしないと定義しています。 The WebXR Device API treats unrecognized, unsupported, or insufficiently consented `requiredFeatures` as conditions that prevent `XRSession` creation, while `optionalFeatures` can be ignored or absent without blocking the session.
  2. MDN の `XRSystem.requestSession()` は Limited availability / experimental / secure context の API として説明され、`NotSupportedError` はモードや required option が未対応の場合にも返り得ると整理しています。 MDN documents `XRSystem.requestSession()` as limited availability, experimental, and secure-context-only, and notes that `NotSupportedError` can also come from unsupported modes or required options.
  3. `hit-test` は WebXR Hit Test Module が追加する feature descriptor で、現実環境への ray intersection を使った配置を可能にしますが、`xr-spatial-tracking` Permissions-Policy の対象です。 `hit-test` is a feature descriptor introduced by the WebXR Hit Test Module for real-world ray intersections, and it is subject to the `xr-spatial-tracking` Permissions-Policy.
  4. DOM Overlay explainer は `dom-overlay` を optional にした場合、セッションは進行し得るが `session.domOverlayState` がなければ DOM が見えない前提で代替 UI を用意すべきだと説明しています。 The DOM Overlay explainer states that an optional `dom-overlay` request may allow the session to continue; if `session.domOverlayState` is absent, the app must assume the DOM is not visible and provide a fallback.
  5. `isSessionSupported()` はモード単位の入口確認には使えますが、feature list の成立までは保証しないため、起動ボタン前に required / optional の判断表を作る価値があります。 `isSessionSupported()` is useful for mode-level entry checks, but it does not prove that a full feature list will be granted, so a pre-launch required / optional decision table is useful.

注目事例と何が面白いかNotable example and why it matters

今日の注目は、XR 体験の失敗を「起動できない」でまとめず、`requiredFeatures`、`optionalFeatures`、Permissions-Policy、ユーザー同意、デバイスサポートに分解して見せることです。W3C の WebXR Device API は required と optional の扱いを明確に分けています。DOM Overlay explainer も、optional overlay が有効でない場合に DOM が見えない前提で代替 UI を持つべきだと示しています。面白いのは、この仕様上の違いを launch UI の表現に変えると、開発者だけでなく展示運用者にも「なぜ fallback したか」が伝わる点です。

Today's notable idea is not treating XR startup failure as a single generic failure. Instead, the sample separates required features, optional features, Permissions-Policy, user consent, and device support. The W3C WebXR Device API draws a clear line between required and optional behavior, and the DOM Overlay explainer says optional overlay usage needs alternate UI when the overlay is absent. The interesting part is turning that specification distinction into launch UI that tells both developers and operators why a fallback path was chosen.

表現・インタラクションのアイデアExpression and interaction idea

サンプルでは feature ごとに off / optional / required を切り替え、device profile、session mode、`xr-spatial-tracking` policy、user activation を操作できます。中央の ladder は mode check、required feature、optional feature、session result を丸い checkpoint として表示します。required が落ちた場合は赤で起動停止、optional が落ちた場合は黄で fallback 継続です。実アプリではこの ladder を起動ボタンの裏側に置き、失敗後にだけ表示する diagnostic panel にできます。

The sample lets you switch each feature between off, optional, and required, then adjust device profile, session mode, `xr-spatial-tracking` policy, and user activation. The center ladder shows mode checks, required features, optional features, and the final session result as checkpoints. A failed required feature blocks launch in red, while a missing optional feature continues through a yellow fallback. In a real app, this can live behind the launch button and surface only as a diagnostic panel after failure.

制作に使えそうな技術メモProduction note

実装時は、`isSessionSupported(mode)` を入口の可否確認に使い、`requestSession(mode, { requiredFeatures, optionalFeatures })` の失敗は DOMException name と要求 feature list を一緒にログ化します。`hit-test`、`anchors`、`depth-sensing` のように `xr-spatial-tracking` に依存する機能は、iframe や埋め込み環境の Permissions-Policy も診断項目に入れます。`dom-overlay` は optional なら `session.domOverlayState` の有無で UI 経路を分け、必須 UI なら required に上げて早く失敗させる方が運用しやすいです。

In production, use `isSessionSupported(mode)` as the entry check, then log the DOMException name and requested feature list when `requestSession(mode, { requiredFeatures, optionalFeatures })` fails. Features such as `hit-test`, `anchors`, and `depth-sensing` depend on `xr-spatial-tracking`, so iframe and embedding Permissions-Policy should be part of diagnostics. If `dom-overlay` is optional, branch UI on `session.domOverlayState`; if the UI is essential, promoting it to required fails earlier and is easier to operate.
