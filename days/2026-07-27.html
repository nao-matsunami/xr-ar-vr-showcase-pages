今日の重要トピックKey topics today

  1. WebXR Raw Camera Access Module は `camera-access` feature descriptor、`XRView.camera`、`XRWebGLBinding.getCameraImage()` を定義し、immersive-ar の camera image を frame と view に結び付けて扱う。 The WebXR Raw Camera Access Module defines the `camera-access` feature descriptor, `XRView.camera`, and `XRWebGLBinding.getCameraImage()`, tying immersive-ar camera images to the current frame and view.
  2. 同仕様は camera image を直接観測できるため privacy impact が高いと位置付け、user consent と privacy indicator を中心的な要件としている。 Because the module exposes direct observation of camera images, it treats privacy impact as high and centers user consent and privacy indicators.
  3. WebXR Device API の基本フローは `isSessionSupported()`、user activation、`requestSession()`、frame loop であり、強い feature を required にする前の capability 判定が体験品質と許可率に効く。 The WebXR Device API flow moves through `isSessionSupported()`, user activation, `requestSession()`, and a frame loop, so capability checks before requiring powerful features affect both quality and permission success.
  4. WebXR Layers API の `fixedFoveation` や layer composition は、camera pixels を全面処理する代わりに gaze 周辺や overlay だけへ処理を限定する設計材料になる。 The Layers API's `fixedFoveation` and layer composition provide design material for limiting processing to gaze regions or overlays instead of processing full camera pixels.
  5. Immersive Web の WebXR samples / Layers samples は、hand tracking、hit test、anchors、projection layer、occlusion、Input Selection Space Warp などを横断して fallback 設計の比較対象にできる。 Immersive Web's WebXR samples and Layers samples provide comparison points across hand tracking, hit testing, anchors, projection layers, occlusion, and Input Selection Space Warp for fallback design.

注目事例と何が面白いかNotable example and why it matters

今日の注目は Raw Camera Access を「使う方法」ではなく「要求する前に避ける方法」として読むことです。仕様上、camera image は frame / view と同期し、`camera-access` は privacy indicator と同意が必要な重い権限です。そこで、camera pixels を要求する前に depth crop、hit test、anchors、lighting、DOM overlay 的な表示で足りるかを選ぶ router をサンプル化しました。

Today's notable angle is reading Raw Camera Access not only as a way to use camera images, but as a reason to avoid requesting them when possible. The spec ties camera images to frame and view, and `camera-access` is a heavy permission with consent and privacy indicators. The sample therefore routes to depth crop, hit testing, anchors, lighting, or overlay-style UI before asking for camera pixels.

表現・インタラクションのアイデアExpression and interaction idea

抽象的な camera grid の上に gaze 領域と routing graph を重ね、`Camera OK / Camera off`、privacy sensitivity、scene motion、feature confidence、frame budget を変えると選択経路が切り替わります。camera を off にしても overlay、depth、hit test、anchor の job が残るため、camera-access に依存しない最小体験の境界をその場で確認できます。

The sample overlays a gaze region and routing graph on an abstract camera grid. Toggling `Camera OK / Camera off` and adjusting privacy sensitivity, scene motion, feature confidence, and frame budget changes the selected path. Even with camera off, overlay, depth, hit-test, and anchor jobs remain, making the non-camera minimum experience visible.

制作に使えそうな技術メモProduction note

実装時は、`requiredFeatures: ["camera-access"]` を最初から指定するより、目的別に fallback を並べた後で最後に camera-access を選ぶ構造にしたいです。例えば、平面配置は hit test と anchors、手前物体の隠れは depth sensing、明るさ合わせは lighting estimation、同意や状態表示は overlay、画質予算は layers / foveation に寄せられます。camera texture を使う場合も保存せず、同一 frame 内で read-only として扱う設計が安全です。

Implementation should list goal-specific fallbacks before adding `requiredFeatures: ["camera-access"]`. Plane placement can use hit testing and anchors, foreground hiding can use depth sensing, relighting can use lighting estimation, consent and state can use overlays, and quality budget can use layers and foveation. If camera textures are used, the safer design is to avoid storage and treat them as read-only within the same frame.
