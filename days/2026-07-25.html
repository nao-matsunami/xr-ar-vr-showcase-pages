今日の重要トピックKey topics today

  1. WebXR DOM Overlays Module の `beforexrselect` は、overlay 上の primary action が DOM UI 操作なのか XR world select なのかを分ける実装上の境界になる。 `beforexrselect` in the WebXR DOM Overlays Module is the implementation boundary for deciding whether a primary action over an overlay is DOM UI interaction or XR world selection.
  2. WebXR Anchors Module は、hit test result から作成した anchor と、frame 上で作成した anchor の両方を扱い、`trackedAnchors` の更新を frame update として扱う。 The WebXR Anchors Module covers anchors created from hit test results and anchors created from a frame, with `trackedAnchors` updated during frame updates.
  3. WebXR Hit Test Module は real world geometry への ray intersection を返すもので、アプリ内 virtual object への当たり判定とは責務が分かれている。 The WebXR Hit Test Module returns ray intersections with real-world geometry and explicitly separates that role from hit testing against application-created virtual objects.
  4. WebXR Depth Sensing は CPU / GPU の depth access path があり、毎フレーム全対象を読むより、入力状態や drift risk に応じた scheduling が実装上の焦点になる。 WebXR Depth Sensing exposes CPU and GPU depth access paths, making scheduling by input state and drift risk more practical than reading depth for every target every frame.
  5. Immersive Web の Layers / Input Selection Space Warp sample は、projection layer、depth、motion vector、input selection の関係を検証する一次デモとして、入力と表示のタイミング差を考える材料になる。 The Immersive Web Layers and Input Selection Space Warp sample is a useful primary demo for studying projection layers, depth, motion vectors, and input selection timing.

注目事例と何が面白いかNotable example and why it matters

今日の注目は、DOM Overlay の `beforexrselect`、Anchors の `trackedAnchors`、Depth Sensing の depth read を同じ入力ゲートに入れる設計です。AR の設定 panel を触っている間に world select を止めるだけだと、裏側の anchor drift や stale depth が進み続けます。そこで UI 操作は保留しつつ、anchor refresh queue は止めない、という運用を 1 画面で見えるようにしました。

Today's notable design combines DOM Overlay `beforexrselect`, Anchors `trackedAnchors`, and Depth Sensing reads in one input gate. If world selection is merely stopped while the user touches an AR settings panel, anchor drift and stale depth keep accumulating behind it. The prototype visualizes a policy where UI interaction is held but the anchor refresh queue keeps running.

表現・インタラクションのアイデアExpression and interaction idea

ステージ上の円を anchor、右上の半透明 panel を DOM overlay として扱います。overlay が blocking のときは、panel 上のタップが `beforexrselect` で world select を止めた状態になります。一方で drift noise、depth budget、input pressure に応じて anchor の age / drift / user proximity を評価し、更新優先度の高いものが queue の上に来ます。

The stage treats circles as anchors and the translucent panel as the DOM overlay. When the overlay is blocking, taps on the panel model `beforexrselect` suppressing world selection. Meanwhile drift noise, depth budget, and input pressure drive each anchor's age, drift, and user proximity so high-priority items rise in the refresh queue.

制作に使えそうな技術メモProduction note

実装では、select gate と refresh scheduler を分けておくと設計しやすそうです。overlay region に入った primary action は DOM 側に吸わせるが、`XRFrame.trackedAnchors` の pose 更新、stale depth の再取得、drift risk の計算は通常 frame loop で続ける。hit test result から新規 anchor を作る経路だけを hold すれば、UI 操作後の再開時に古い深度で配置してしまう事故を減らせます。

A practical implementation should separate the select gate from the refresh scheduler. Primary actions inside overlay regions can be consumed by DOM, while `XRFrame.trackedAnchors` pose updates, stale-depth reads, and drift-risk scoring continue in the normal frame loop. Holding only the path that creates new anchors from hit test results reduces the chance of placing against old depth after UI interaction ends.
