今日の重要トピックKey topics today

  1. WebXR Raw Camera Access Module は `camera-access` feature descriptor を追加し、immersive-ar session の背後に表示される camera image を `XRView.camera` と `XRWebGLBinding.getCameraImage()` から扱う設計になっている。 The WebXR Raw Camera Access Module adds the `camera-access` feature descriptor and exposes the camera image behind an immersive-ar session through `XRView.camera` and `XRWebGLBinding.getCameraImage()`.
  2. Raw Camera Access は `xr-spatial-tracking` と `camera` の permissions policy に関係し、同意と privacy indicator が中心的な要件になるため、便利な認識処理より先に露出範囲を絞る設計が必要になる。 Raw Camera Access involves both `xr-spatial-tracking` and `camera` permissions policy, with consent and privacy indicators as central requirements, so limiting exposure should come before convenient recognition processing.
  3. WebXR Augmented Reality Module の secondary views は、録画や配信用の first-person observer view を扱うための拡張で、通常の左右 eye view だけを前提にしない render loop が必要になる。 Secondary views in the WebXR Augmented Reality Module support first-person observer views for capture or streaming, requiring render loops that do not assume only the two eye views.
  4. WebXR DOM Overlays は overlay を最上位 content layer として合成するため、camera-access indicator や同意 UI と world input の境界を設計する上で引き続き重要になる。 WebXR DOM Overlays composite overlay DOM as the topmost content layer, so they remain important when designing the boundary between camera-access indicators, consent UI, and world input.
  5. Immersive Web の Layers samples は projection / quad / media / occlusion / Input Selection Space Warp を横断的に確認でき、camera texture、depth、foveation、input timing を同じ予算表で見る材料になる。 The Immersive Web Layers samples cover projection, quad, media, occlusion, and Input Selection Space Warp, making them useful references for looking at camera texture, depth, foveation, and input timing in one budget table.

注目事例と何が面白いかNotable example and why it matters

今日の注目は Raw Camera Access です。WebXR の中で camera image の pixel に近づける API は、深度や hit test よりも privacy impact が大きいので、単に texture を取れるかではなく、同意、indicator、mask、処理頻度まで含めて機能として扱う必要があります。そこで、camera texture job を gaze / hand / anchor / depth の queue に入れ、privacy mask が強いほど camera job の有効画素を落とすサンプルにしました。

Today's notable item is Raw Camera Access. An API that gets close to camera-image pixels has a larger privacy impact than depth or hit testing, so the feature needs to include consent, indicators, masking, and processing frequency rather than only texture availability. The sample puts the camera texture job into the same queue as gaze, hand, anchor, and depth work, reducing effective pixels as the privacy mask increases.

The full stage acts as an abstract AR camera background, with the upper-left indicator standing in for the camera-access privacy indicator. Dragging moves the gaze center, while hand proximity and head motion change job priority. Switching `Consent / Deny` stops only the camera texture job; privacy mask, depth crop, anchor refresh, and hand pinch remain separate jobs.

制作に使えそうな技術メモProduction note

実装では `camera-access` を required feature にする前に、同じ体験を depth sensing、hit test、anchors、lighting estimation で代替できないかを先に判断したいです。使う場合も `XRView.camera` は frame と view に紐づくため、texture を永続保存しない、同一 frame 内の読み回しに閉じる、overlay で indicator を常時見せる、foveation や gaze によって処理領域を限定する、といった制約を scheduler に入れておくと扱いやすそうです。

Before making `camera-access` a required feature, implementation should first check whether depth sensing, hit testing, anchors, or lighting estimation can satisfy the experience. If camera access is necessary, `XRView.camera` is tied to frame and view, so the scheduler should avoid persistent texture storage, keep reuse within the same frame, keep an overlay indicator visible, and limit processing regions through foveation or gaze.
